# Technical decisions

Short log of choices that `CLAUDE.md` left open or that changed. One row per decision, with a number, a date and a one-line reason. To change a decision, add a new row that supersedes the old one. Do not delete old rows.

|---|---|---|---|
| D-001 | 2026-10-29 | Data access with **Kysely** + `kysely-codegen` (types generated from the database). Migrations are **plain numbered SQL files**, run by a small script in `apps/api`. | The data model has a lot of hand-written SQL (RLS, triggers, routines with `FOR UPDATE`, `SET LOCAL`). Kysely keeps the transaction and the RLS context explicit and does not hide the SQL. |
| D-002 | 2026-10-29 | **Tailwind CSS v4** with shadcn/ui. | The starter tokens in `CLAUDE.md` already use `@theme inline`. |

| D-021 | 2026-10-31 | Phase B sign-in is simulated in `apps/web/src/data/auth.ts` with the real rules and the error codes of `API.md`: only +55 mobiles (RN-AUT-01), 5 wrong attempts then a 15 minute lock (RN-AUT-02), 3 requests per number (RN-AUT-03), same answer for new and existing numbers (RN-AUT-05). | D-022 | 2026-10-31 | Supersedes the fixed code `123456` of D-021. The simulated sign-in generates a random 6 digit code per request and per number, valid for 5 minutes, single use, and replaced by the next request (RN-AUT-02). It prints the code in the browser console, in development only (never in a production build). Time comes from an injectable `Clock` (`apps/web/src/lib/clock.ts`), so expiry, the hourly limit and the 15 minute lock are tested with a simulated time. After a wrong code the focus returns to the code field with all digits selected. | Tiago wants to see the OTP working before the SMS exists. This is a deliberate, temporary exception to golden rule 8 of `CLAUDE.md` (never log SMS codes): it exists only in the web simulation, and the real API must never log codes. |
| D-023 | 2026-11-01 | API (`apps/api`): NestJS 12 on Express, ESM, run in development with `tsx` and built with `tsup` (both esbuild). esbuild does not emit decorator metadata, so injection is always explicit (`@Inject(TOKEN)`) and validation uses our own `ZodValidationPipe` with the schema passed in (`@Body(new ZodValidationPipe(schema))`) instead of `nestjs-zod`. Logs with `pino`, with a fixed list of redacted keys (golden rule 8). `GET /health` stays outside `/v1`. | Keeps one fast toolchain for dev, tests (Vitest) and build, with no `emitDecoratorMetadata`, and fewer dependencies than `nestjs-zod`. Supersedes the suggestion of `nestjs-zod` in `CLAUDE.md`. |
| D-024 | 2026-11-01 | Database access in `apps/api`: `pg` with Kysely, plain SQL migrations in `apps/api/migrations/` run by our own small runner (`pnpm db:migrate`) that saves a checksum and refuses an applied file that changed. The two roles are created by migration `0001_roles.sql` without a password; the runner sets the passwords found in `DATABASE_URL` and `DATABASE_URL_SYSTEM`, so no secret is in a migration. A third URL, `DATABASE_URL_MIGRATE`, is the owner of the tables. `app_user` has no right to create or drop anything. Tests: Vitest has two projects, `unit` (no database) and `integration` (`*.int.test.ts`, Postgres 16 in a container through Testcontainers, one fresh database per test file). | Matches D-001 and `DATA_MODEL.md` section 9. Keeping the passwords out of the migrations and the owner apart from the two roles makes the isolation of golden rule 1 hold even if application code is wrong. |
| D-025 | 2026-11-01 | `customers` has only the read policy `customer_self`; `app_user` has no `INSERT`, `UPDATE` or `DELETE` on it. The tables `sessions`, `otp_codes`, `phone_lockouts` and `sms_messages` have no right at all for `app_user`: only `app_system` uses them. Primary keys default to `gen_random_uuid()`. | `DATA_MODEL.md` section 9 contradicts itself on customer writes (policy `customer_self_update` versus writes through `app_system`). The safer reading was followed. Tiago can flip it with one new migration. |
| D-026 | 2026-11-01 | Migration `0003` creates `businesses`, `staff`, `programs`, `business_customers`, `enrollments`, `cycles`, `stamps`, `redemptions` and `qr_tokens`, each with RLS enabled and forced (except `qr_tokens`, which only `app_system` uses). `staff` and `redemptions` came earlier than the plan said (T20 listed neither), because `stamps` points to `staff` and the seed needs a prize. The customer may read its own enrollments, cycles, visits, prizes and links, plus the business and card of an enrollment of its own, and writes nothing. Corrections to `DATA_MODEL.md`: the `CHECK` of a reversal now requires `reason IS NOT NULL` (a null `length()` made the CHECK pass), and the end-of-day formula casts to `timestamp` before `AT TIME ZONE` (the date was read in the session time zone). `businesses.slug` cannot change (trigger) and must be lowercase words with hyphens. `businesses.category` is a nullable text. | Found by the tests of T20. Both formulas would have broken RN-EST and RN-VAL-04 later. The slug and category follow RN-TEN-05 and the card of the design. |
| D-027 | 2026-11-02 | The SMS code of the customer: `OtpSender` interface (RN-AUT-04) with a `console` provider that prints the code in the API terminal and refuses to run outside `NODE_ENV=development` (extends the temporary exception of D-022 to the API). The code is kept as an HMAC-SHA256 of number and code with `OTP_HASH_SECRET`, never plain. Limits per number (3 per hour) and per IP (20 per hour) are counted from `otp_codes` and guarded by two Postgres advisory locks (number, then IP) inside one transaction, so concurrent requests cannot pass a limit together. The SQL of the codes lives in `src/system/otp.repository.ts` (role `app_system`); the rules live in `customer-auth/otp.service.ts`. `@fregues/shared` is bundled into the API build (`tsup.config.ts`) because it is TypeScript source. A variable left empty in `.env` counts as not set. `TRUST_PROXY_HOPS` tells how many proxies stand in front, so the limit per IP sees the real address. | The plain hash of 6 digits would be reversible in a blink; the locks make the limits true under load (proved by tests that fail without them). Without `TRUST_PROXY_HOPS` every customer would share one IP and one limit behind a proxy. |
| D-028 | 2026-11-02 | Customer session: access token is a JWT HS256 of 15 minutes (`jose`, claims `sub` and `typ`, times from the `Clock`); the refresh token is 32 random bytes in an `HttpOnly; SameSite=Lax` cookie limited to `/v1/customer/auth`, kept as a SHA-256 hash. Each refresh revokes the used row and inserts a new one with the same `family_id` (new migration `0004`), 90 days from the last use. A row that was already revoked being shown again revokes its whole family. The row of a refresh is locked with `FOR UPDATE`, so two requests with the same token cannot both rotate it. Confirming a code runs under the advisory lock of the number, and a wrong attempt and the lock are saved before the error is raised. The customer is created when its first code is confirmed. `COOKIE_SECRET` is not needed (the cookie holds a random token, not a signed value) and was removed from `.env.example`. | Matches API.md section 1 and RN-AUT-02/06. The family keeps "reuse revokes the session" possible with one row per token and no change to the shape of the table beyond one column. |
| D-029 | 2026-11-02 | Customer profile (`GET` and `PATCH /v1/customer/me`): a guard (`CustomerAuthGuard`) verifies the access token with `AccessTokenService` and hands the id (`sub`) to the handlers; `TOKEN_EXPIRED` for an expired token, `UNAUTHENTICATED` for any other. The read runs as `app_user` under the customer context (the `customer_self` policy shows only the own row); the write runs as `app_system` (D-025) in `src/system/customer.repository.ts`, in one transaction with the row locked. The version of the Terms is a constant in `@fregues/shared` (`TERMS_VERSION`, `2026-10-01`, the value of the example in API.md); the server records it with the date from the `Clock`, and the first acceptance is never overwritten. | The id never comes from the body or the URL, so a customer cannot reach another one. One shared constant keeps the app and the server on the same version of the Terms. |
